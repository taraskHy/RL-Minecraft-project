Minecraft parkour · deep reinforcement learning · technical notes

How the Parkour Bot Learned

A network of about 300,000 weights learned to run Minecraft parkour courses it had never seen, from trial and error in a simulator, and then ran them in the real game. This page explains how: what it sees, what it is rewarded for, the algorithm that trains it, where that algorithm got stuck, and what fixed it.

1The short version

Kind of learning

Deep reinforcement learning with PPO: model-free, on-policy, actor-critic. It never learns a model of the physics; it learns which action to take from what it sees.

How it practised

16,384 games at once in an exact copy of Minecraft's movement physics on the GPU: 1.57 billion game ticks for the main run, about 2 hours on one RTX 5080.

What it was paid for

Getting closer to the goal along the course, +1 per new platform, +10 at the goal, −5 for falling, −0.01 per tick.

Where it got stuck

Neo jumps (around the end of a wall): it learned to stand still instead. Imitating a search-based planner (behaviour cloning, then DAgger) taught them.

The final policy completes 98.4% of unseen standard courses and 95.2% with obstacles (simulator, test sets played once), and in real Minecraft it finished exactly the courses the simulator said it would. The rest of this page goes one layer down at a time.

2The world it learned in

A course is a chain of stone platforms floating in the void. The player starts on platform 0 and must reach the last one. Courses are generated at random, so every test course is new to the agent.

Training in the real game would be far too slow (20 ticks per second, one player). Instead, the project ported prismarine-physics, the engine a Mineflayer bot uses to move, to batched PyTorch on the GPU. The port keeps every expression and its operand order in 64-bit floats, so it is not an approximation: over 99,000 random ticks against the real library, the largest position error was 1.4e-14 blocks (results/physics_parity.json). The simulator runs about one million game ticks per second.

Two properties of this world shape everything below:

  • It is deterministic. The same state and action always give the same next state. The only randomness in training is which course is drawn and which action the policy samples.
  • It is exact. Whatever the network learns in the simulator is what happens in Minecraft. There is no simulation-to-reality gap to bridge, only rounding error.

3What it sees and does

Reinforcement learning frames the task as a Markov decision process: at every step the agent observes the state, picks an action, the world moves on, and a reward comes back. Here a step is one game tick (50 ms), the same rate a human player's inputs are read at.

The observation: 255 numbers

The network never sees the whole course. Each tick it gets 255 numbers, measured in the player's own frame (so "ahead" is always the same direction to it):

Own motion (6): velocity, on the ground or not, jump cooldown, touching a wall sideways. Previous action (5): what it pressed last tick. Platforms (44): the platform it last stood on and the next three: the four corners of each top face, its height, whether it is the goal. Block scan (196): floor height and a ceiling flag at 98 points, from 1 block behind to 5.5 ahead and 1.5 to each side. Goal (3): where the goal is. Progress (1): the fraction of platforms reached.

Because platforms beyond the next three, and obstacles outside the scan, are hidden, the agent technically faces a partially observable problem (a POMDP), and it plays it with a memoryless network. Each input is standardised by a running mean and variance and clipped to ±5 before the network sees it.

The action: 252 combinations, chosen as 5 independent choices

Moveback · none · forward
Strafeleft · none · right
Jumpno · yes
Sprintno · yes
Turn−20 −6 −1.5 0 1.5 6 20°

The network outputs 17 numbers, one per option, split into five softmax distributions. It picks each part independently and the probability of the whole action is the product: 3 × 3 × 2 × 2 × 7 = 252 combinations. A policy that knows nothing picks uniformly, and its entropy is ln 252 = 5.53. The main run's first iteration logged 5.52, its last 2.15 (results/runs/main-g995/train_log.csv): training is the policy becoming more certain.

The network

Two separate multilayer perceptrons, each 255 → 512 → 256 → 128 with ELU activations: the actor ends in the 17 action logits, the critic in one number, its estimate of how much reward is still to come from this state (the value). The critic is only used during training; the bot runs the actor alone and takes the most likely option of each part.

4The reward

The reward is the only thing that tells the agent what "good" means. The project started from three ideas (distance to the goal, number of jumps, height) and made each one a term. The reward for one tick is:

rt = 1 · (dt−1 − dt) progress: how much shorter the path to the goal got + 1 · (kt − kt−1) landing: +1 per new platform reached (skipped ones count) + 10 · [goal reached] ends the episode − 5 · [fell] ends the episode − 0.01 time: every tick costs a little

d is the remaining path length: the distance from the feet to the next platform's top centre, plus the centre-to-centre distances from there to the goal. Measuring along the course rather than straight to the goal is what makes winding courses work. k is the furthest platform stood on.

6The algorithm: PPO

Proximal Policy Optimization is a policy-gradient method: it nudges the network to make actions that turned out better than expected more likely, and worse ones less likely, without moving too far from the policy that collected the data. One training iteration:

  1. Collect. 16,384 games run in parallel for 32 ticks each: 524,288 (observation, action, reward) samples. Actions are sampled from the policy, which is how it explores. A finished game restarts at once on a new course.
  2. Score each action (GAE). For every sample, compute the advantage: how much better the outcome was than the critic expected.
  3. Update. 4 passes over the samples in 8 minibatches, adjusting both networks to lower the loss below.

Advantages: generalised advantage estimation

δt = rt + γ · V(st+1) · (1 − donet) − V(st) one-step surprise Ât = δt + γλ · (1 − donet) · Ât+1 γ = 0.995, λ = 0.95 Rt = Ât + V(st) the critic's target

A cut-off by the stall rule is not a real ending, so the value of the last state is still counted (bootstrapped). A fall or the goal is a real ending, so nothing follows it. The advantages are normalised per batch.

The loss

ρ = πnew(a|s) / πold(a|s) log-ratio clamped to ±20 Lπ = −mean( min(ρ·Â, clip(ρ, 0.8, 1.2)·Â) ) clipped surrogate, ε = 0.2 where Â < 0: max(that, 3·Â) dual clip LV = ½ · mean( max((V − R)², (Vclip − R)²) ) value clipped like the policy L = Lπ + 1.0 · LV − 0.005 · H(π) H: entropy, keeps it exploring

The clip stops one batch of lucky samples from changing the policy too much. The dual clip, the log-ratio clamp, a stop when one minibatch moves the policy more than KL 0.05, and a learning rate that adapts to keep the per-minibatch KL near 0.01 (between 1e-5 and 1e-3) were all added after the first runs collapsed three times: the policy change jumped from about 0.004 to 0.3, 1.3 and once infinity, and training success fell from about 75-80% to 15-17% within two iterations. With these four safeguards, no collapse came back.

Why PPO and not a table or a planner? The state is continuous and every course is a new geometry, so a lookup table cannot generalise; a function approximator (the network) is required. Search-based planning does work (section 9 uses it), but it needs the exact simulator at play time and seconds of computation per jump. The network decides in microseconds from what it sees.

7Learning over time

At iteration 1, the policy is uniformly random: 99.9% of its games end in a fall and it collects −5.4 per game on average. By the end it finishes 96.7% of its training games, with an average return of +53.6 (train_log.csv).

8The discount and the horizon

A reward n ticks in the future counts γn as much as one now. That single number decides how far ahead the agent "cares". Move the slider:

0.134weight with γ = 0.99 (the default)
0.367weight with γ = 0.995 (the final policy)

How much a future reward counts

A 10-jump course takes 120 to 200 ticks. With γ = 0.99 the +10 goal bonus is worth 30% to 13% of its value at the start; with 0.995, 55% to 37%, so the far goal pulls harder. In a sweep of one setting at a time, γ = 0.995 was the only change that beat the defaults by 3 points on validation in all three seeds (95.4% against 91.8%; level 5 on test: 76.3% against 72.0%), so the final policy uses it (configs/sweep_hparams.json).

9Where PPO failed: neo jumps

A neo is a jump around the end of a wall: take off beside it, swing around its end in the air, land on the far side. It is possible but extremely tight: a cross-entropy search found a landing for 16 of 18 single-neo layouts, but only 1 in 2,000 to 16,000 sampled action sequences landed.

The diagnosis: the agent learned to refuse

Trained on courses with neos, the policy made none of the 13 single-neo jump types from a standing start: on 11 of them it stood still until the 200-tick stall rule every time. Under this reward that is the rational choice:

Refusing costs only the time penalty: 200 ticks × 0.01, and the cut-off is bootstrapped, so the agent keeps the value of where it stands.

Trying almost never lands for a policy exploring at random, and a miss costs −5 and ends the game.

The fall penalty that helped most on normal courses (section 5) is exactly what taught the refusal here. The real game in section 4's chart shows it: platform 1, then 200 ticks of nothing.

A stall penalty did not fix it. Making the stall end the game with −5 should have removed the incentive, but with γ = 0.99 a penalty 200 ticks away counts only 0.99200 = 0.13 (see the slider). After 1,000 iterations the policy still made none of the 13 types.

The fix: learn from a teacher

  1. Demonstrations. A cross-entropy search over the bot's own 252 actions, using the exact simulator, found 50,706 landing action sequences.
  2. Behaviour cloning beside PPO. An imitation term is added to the PPO loss, pulling the policy towards the searched actions:
    L = LPPO + w · ( −log π(ateacher | s) ) w = 1, later 0.3
    Now the policy made all 13 types from a standing start (54.8% of attempts).
  3. DAgger. On a real course the bot reaches a neo moving, not from rest, in states the demonstrations never covered. DAgger (Ross et al., 2011) fixes this: let the policy play, and at every neo takeoff it actually reaches, ask the search for a landing from that exact state. Add those (state, action) pairs to the data and train again.

10Skills for hard pieces

Training a policy to do neos itself levelled off near 30% of neo courses. What worked better was a division of labour: the final policy plays every ordinary jump, and a skill, a second network of the same shape, plays only the hard piece. A fixed rule (the course list's neo detector, or the router's choice) hands control over and takes it back, much like an option in hierarchical reinforcement learning.

How a skill is trained

  • Short episodes. An episode is only the piece's block: from the platform before the takeoff to the platform after the target (train.py --segments). Reaching the end is the goal; skipping a platform of the block counts as a fall; otherwise the reward is the same as above.
  • Real starting states. Each episode starts in a state where the final policy really arrived on such courses: a bank of tens of thousands of exact states, collected by letting the final policy play.
  • Practice where it fails. Each piece type is drawn with weight 0.25 + its failure rate, so hard types come up more often.
  • PPO plus a teacher. PPO on these episodes, and for the hardest types, DAgger labels from the planner at the skill's own takeoffs and in its own flight (imitation weight 0.3).

11The router: learning the route

Everything above gets the course list: it is told which platform comes next. The router removes that. It is a second, higher-level policy that looks at the platforms in view and picks the next one; the final policy then jumps there. This is hierarchical reinforcement learning, built on the teammate's PC.

  • Decisions only at the start and after each landing on a new platform: a semi-MDP, where one action lasts many ticks.
  • Observation: one token per platform in view (position, size, gap, height change, flags), plus global numbers.
  • Network: a small set transformer (2 layers, width 128, 4 heads, no position encoding, so the order of the tokens does not matter) that scores each selectable platform: a pointer network.
  • Reward: the environment's own reward summed over the ticks until the next decision, discounted 0.997 per tick, with −5 if the game ends by the stall or time limit.
  • Training: PPO plus an imitation term towards the course's next platform. The course is used for the reward and this training signal only, never as an input.

Result: 97.8% of standard and 95.0% of obstacle test courses (simulator, played once), against the hand-written greedy planner's 92.3% and 90.5%; in real Minecraft 57/60 and 56/60. The honest finding: once warm-started, most of the router's quality came from the on-policy imitation, and PPO without it drifted down (results/routing/README.md).

12One network for every skill

Separate specialists were trained for the basic levels, the advanced levels (neos, run-ups, wide jumps) and the new blocks (head hitters, ice, shaped blocks, slime, ladders). Policy distillation then trained one student network with PPO plus a term that pulls its action distribution towards the right teacher's on each course:

L = LPPO + w · KL( πteacher(·|s) ‖ πstudent(·|s) )

The one network (results/combined_policy.pt) averages 86.4% over the four skill groups on test, a match for the best specialist of each group, and plays the final policy's real-game courses at 59/60 and 59/60.

13From simulator to real Minecraft

The trained actor is exported as JSON and run in JavaScript inside the bot's physics tick. After each tick the bot builds the same 255 numbers from what the game shows it (checked against the Python version to float32 rounding), takes the most likely action and sets its controls. The bot only builds the course and teleports to the start with server commands; during a run it uses movement controls only.

Because the simulator is exact, two checks follow every real run: the replay check re-simulates the recorded actions and compares positions tick by tick (largest difference 2.1e-14 blocks on the main runs), and the policy check plays the same course in the simulator and compares outcomes. In the 448 recordings on the replay page, every outcome matched the simulator's, with 0 server corrections; across all of the project's real-game runs a few server corrections did happen, at a wall's corner, where the game's collision order can differ from the simulator's. The real-Minecraft replays show 448 of them in 3D.

14Glossary

Policy (actor)
The network that maps an observation to a probability for each action.
Value (critic)
The network's estimate of the discounted reward still to come from a state.
Advantage
How much better an action turned out than the critic expected; positive advantages make the action more likely.
On-policy
Learning only from data the current policy collected; PPO discards each batch after its update.
Model-free
Learning what to do without learning how the world moves.
Entropy
How spread out the action probabilities are; ln 252 = 5.53 means fully random.
Bootstrapping
Using the critic's value of the last state in place of the rewards that were cut off.
Curriculum
Ordering training from easy to hard, here by the jumps' forgiveness.
Behaviour cloning
Supervised learning of a teacher's actions: maximise log π(ateacher|s).
DAgger
Dataset aggregation: label the states the learner itself visits with the teacher's actions, so it learns to recover from its own mistakes.
Distillation
Training a student to match teachers' action distributions.
Semi-MDP / option
A decision that lasts many ticks: the router's choice of platform, a skill's whole block.
Validation / test
Separate held-out course families: choices are made on validation, and each test set is played once and only reported.
